# 功能分析与问题诊断

> 本文档对应面试任务中的「功能分析」与「问题诊断」两项要求，
> 分析对象为参考原型 `coding-interview/Data/index.html`（单文件，约 4000+ 行）。

---

## 一、功能分析

### 1.1 产品定位

「AI 问数」是一个企业级销售经管数据管理平台，核心能力是**数据问答**：
用户用自然语言提问，平台完成「查询 → 分析 → 可视化」全流程，将结果以
表格 + 图表 + 文字解读的形式返回，降低非技术人员访问经营数据门槛。

### 1.2 原型包含的三大模块

| 模块 | 职责 | 关键交互 |
|---|---|---|
| **智能问数**（核心） | 对话式数据问答 | 侧边栏会话管理、欢迎页示例问句、提问框、AI 回答卡片 |
| **驾驶舱报表** | 固定维度的可视化报表 | 多个图表页（经营指标、销售达成等） |
| **系统管理** | 平台配置 | 模型配置、应用配置、账号配置、反馈管理 |

### 1.3 智能问数页交互拆解（重点）

**页面结构**：
- **左侧会话侧边栏**：近 30 天记录列表、置顶/删除、开启新对话。
- **欢迎页**（无对话时）：问候语 + 描述 + 「你可以这么问我」示例问句卡片（点击即提问）。
- **对话区**：
  - 用户消息：右侧蓝色气泡，支持复制、编辑、重新发送。
  - AI 回答卡片（`qa-ai-card`）包含 6 个部分：
    1. **分析过程**（可折叠）：5 步流程（选择数据表 → 推理逻辑 → 执行取数 SQL → 展示结果 → 执行结束）。
    2. **数据发现**：指标要点列表。
    3. **数据表格**：查询结果明细。
    4. **数据统计**：记录数 / 平均值 / 最大值 / 最小值。
    5. **数据可视化**：图表（原型为 CSS 手绘柱状图）。
    6. **底部**：操作按钮（复制/反馈/语音播报）+ 「耗时 + Token + 时间」统计 + 追问建议 chips。
- **输入栏**：快捷提问（常问/收藏 tab）、文本输入（Enter 发送）、语音按钮、发送按钮。

**核心链路**（理想态）：`提问 → 理解 → 生成 SQL → 查库 → 表格/图表 → 解读`。

### 1.4 交互逻辑要点

- `navigateTo(page)` 切换页面；`sendChat()` 发送问题并追加用户气泡。
- AI 回答由 `genAiReply()` 生成（**当前为写死的 mock**），随后 `appendAiReply()` 追加。
- 会话与消息存储于 `localStorage`（`saveQaSessions`），无后端持久化。
- 快捷提问、追问 chips、反馈、语音等均为可选项或占位。

## 二、问题诊断

以下问题均来自对原型源码的通读，按严重程度分级。

### 2.1 严重问题（影响核心功能成立）

1. **AI 回答是硬编码模板，与问题无关**
   源码 `genAiReply()` 固定返回「北京代表处 / 上海代表处…」等经营单元数据，
   无论用户问什么，回答内容都不变，`data-question` 仅做占位。核心的
   「自然语言 → SQL → 查询」能力**完全缺失**。

2. **无后端、无真实数据源**
   所有数据由 `genMockRow()` 等函数在前端临时生成，无数据库、无查询引擎、
   无 Text2SQL。所谓「问数」名不副实。

3. **无 SQL 生成与安全校验**
   原型的「分析过程」里展示的 SQL 是写死的演示文本；真实实现需要生成 SQL
   并做安全校验（仅允许只读查询、防注入），原型完全没有。

### 2.2 一般问题（影响可信度与可维护性）

4. **「耗时 / Token」是写死字符串**
   底部「耗时 0.6s Token:342」直接硬编码在模板里（约第 2730 行），
   与真实调用无关，属于误导性展示。

5. **语音功能是空壳**
   麦克风按钮 `onclick=""`、语音播放按钮无任何实现，点击无响应。

6. **单文件 4000+ 行、无组件化**
   全部 HTML/CSS/JS 挤在一个文件，无模块拆分、无状态管理，
   难以维护和扩展，也不符合工程化规范。

7. **数据持久化仅 localStorage**
   会话/配置/反馈均存本地，无法多端同步、无用户隔离，无法支撑「企业级」。

### 2.3 备注项（README 明确为可选项，故不计为缺陷）

- 登录 / 用户管理：README 注明「不需要实现」。
- 语音转文字、文字转语音：README 注明为「可选项」。

## 三、本项目的应对方案

针对上述诊断，本实现做了如下对应（详见 `README.md`）：

| 原型问题 | 本实现方案 |
|---|---|
| AI 回答硬编码 | 接入大模型 API，真实生成 SQL 与解读 |
| 无后端 / 无数据源 | FastAPI + SQLite 真实数据库，`data/seed.py` 造数 |
| 无 SQL 安全校验 | `text2sql.py` 只放行 SELECT/WITH + 关键字拦截 + 只读连接 |
| 耗时/Token 写死 | 前端真实计时 + 后端返回真实行数 |
| 单文件不可维护 | React 组件化拆分 + Vite 构建 |
| 无持久化 | SQLite 数据库持久化（会话历史可在后端扩展） |
| 模型生成 SQL 可能出错 | 失败自动重试：报错喂回模型自我修正 |
